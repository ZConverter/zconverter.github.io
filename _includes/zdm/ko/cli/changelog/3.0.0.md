ZDM-API 3.0.0 의 응답 형식 변경에 대응했습니다. **API 버전과 무관하게 동작하므로 업그레이드 순서를 맞출 필요가 없습니다** — 구버전 API 와도 그대로 동작합니다.

---

**신규 — `recovery image-regist`**

Source 서버 없이 backup image 파일명만으로 복구 작업을 등록합니다. Source 서버가 ZDM 에서 삭제된 뒤에도 이미지가 저장소에 남아 있으면 복구할 수 있습니다.

```bash
zdm-cli recovery image-regist \
  --backup-file "server01_ROOT_0262.ZIA,server01_boot_0262.ZIA" \
  --target "t-rocky9_192.168.3.104" \
  --platform oci --mode full --repository-id 9
```

자세한 옵션은 [recovery image-regist](/zdm/ko/cli/3.0.0/docs/recovery/image-regist) 참조.

---

**신규 — `backup image list`**

`recovery image-regist` 의 `--backup-file` 에 넣을 **이미지 파일명을 찾을 방법이 없던 문제**를 해결합니다. 저장소에 저장된 backup image 파일 목록을 조회합니다.

```bash
zdm-cli backup image list --server web01 --names-only
```

- 모든 center / 여러 center / 특정 center(기본값은 config 의 `zdm.id`) / 특정 center 의 특정 저장소, 네 가지 범위로 조회할 수 있습니다.
- `--names-only` 옵션은 파일명만 콤마로 이어 한 줄로 출력합니다 — `recovery image-regist --backup-file` 값으로 그대로 붙여 쓸 수 있습니다.
- 저장소마다 데몬이 직접 스캔하므로 시간이 걸립니다. `--repository-id` 로 저장소 하나로 좁히면 빨라집니다.

자세한 옵션은 [backup image list](/zdm/ko/cli/3.0.0/docs/backup/image-list) 참조.

**신규 — `zdm list` 의 부가 정보 옵션 4종**

`zdm list` 가 Disk · Partition · Network · ZOS Repository 정보를 함께 조회할 수 있습니다. 종전에는
Repository 만 가능했습니다.

```bash
zdm-cli zdm list --disk --net
zdm-cli zdm list --partition
zdm-cli zdm list --zos-repo
```

| 옵션 | 별칭 |
|---|---|
| `--disk` | - |
| `--partition` | - |
| `--network` | `-net` |
| `--zos-repository` | `-zos-repo` |

지정한 항목만 응답에 실립니다. 여러 개를 함께 지정할 수 있습니다.

자세한 옵션은 [zdm list](/zdm/ko/cli/3.0.0/docs/zdm/list) 참조.

**동작 변경 — `zdm list --detail` 이 실제로 상세 정보를 표시**

```bash
zdm-cli zdm list --detail
```

```
resources.model        : PowerEdge R740
resources.cpu          : Intel(R) Xeon(R) Gold 6248
resources.cpuCount     : 2
resources.memory       : 34359738368 (32.00 GB)
resources.kernel       : 5.15.0-91-generic
resources.systemType   : x86_64
resources.organization : ZConverter
```

**ZDM-API 3.0.0 이상이 필요합니다** — 이 항목만은 구버전 API 와 동작하지 않습니다.

**신규 — 전역 옵션 `--config` · `--debug` · `--quiet` 와 자동완성**

모든 커맨드에서 쓸 수 있는 전역 옵션 셋과 셸 자동완성이 추가됩니다.

| 옵션 | 별칭 | 설명 |
|---|---|---|
| `--config <경로>` | - | 사용할 설정 파일을 직접 지정 |
| `--debug` | `-d` | 진단 상세 출력 |
| `--quiet` | `-q` | 진단 억제 (오류 메시지는 유지) |

```bash
# 설정 파일을 직접 지정
zdm-cli --config /opt/zdm/zdm-cli-config.json server list

# 자동완성 스크립트 생성
zdm-cli completion >> ~/.bashrc
```

- **`--config` 를 주면 그 경로만 봅니다.** 파일이 없으면 다른 위치를 찾지 않고 설정 오류(종료 코드 `5`)로
  끝납니다 — 지정한 파일이 없는데 엉뚱한 설정으로 동작하는 일이 없습니다.
- `--debug` 는 **어느 설정 파일을 읽었는지**도 표시합니다. 이 CLI 는 심볼릭 링크로 아무 디렉터리에서나
  실행되고 **설정 탐색 1순위가 현재 디렉터리**이므로, 그 자리에 오래된 `zdm-cli-config.json` 이 있으면
  설치본이 아니라 그것이 쓰입니다. 의도한 설정이 맞는지 확인할 때 쓰세요.
- `--debug` 와 `--quiet` 를 함께 주면 `--debug` 가 우선합니다.
- `--debug` 는 종전에 `LOG_LEVEL=debug` 환경변수로만 가능했습니다. 환경변수도 계속 동작합니다.

**신규 — 종료 코드 공개**

종료 코드는 스크립트·CI 와의 계약인데 지금까지 문서화된 적이 없었습니다. 이번에 표를 공개하고,
공개하기 전에 어긋나 있던 매핑을 바로잡았습니다.

| 코드 | 뜻 | 예 |
|---|---|---|
| `0` | 성공 | |
| `1` | 일반 실패 | 파일 읽기/쓰기 오류, 분류되지 않은 오류 |
| `2` | 사용·입력 오류 | 알 수 없는 옵션, 커맨드 누락, 필수 값 누락, 잘못된 형식(스케줄·JSON 포함) |
| `3` | 인증·권한 | 토큰 만료/누락, 접근 거부 |
| `4` | 네트워크 | 서버 접속 불가, 요청 타임아웃 |
| `5` | 설정 | 설정 파일 없음/파싱 실패, 설정 값 누락 |
| `6` | 플러그인 | (현재 발생하지 않음 — 예약) |
| `7` | 서버 | API 5xx |
| `130` | 사용자 중단 | Ctrl+C (`128 + SIGINT`) |
| `143` | 외부 종료 | SIGTERM (`128 + SIGTERM`) |

**바뀐 값이 있습니다.** 종전에 아래 세 가지가 모두 `1` 이었습니다.

| 상황 | 이전 | 이후 |
|---|---|---|
| 알 수 없는 옵션 · 커맨드 누락 등 사용 오류 | `1` | **`2`** |
| 스케줄 입력 형식 오류, `config set` 값 형식 오류 | `1` | **`2`** |
| 설정 파일 없음 / 파싱 실패 | `1` | **`5`** |

루트 `zdm-cli --help` 말미에도 한 줄 요약이 나옵니다.

**동작 변경 — Ctrl+C 중단이 성공으로 보고되던 문제 (CI·스크립트 확인 필요)**

Ctrl+C 로 중단해도 종료 코드가 **`0`(성공)** 이었습니다. 호출한 스크립트와 CI 는 작업이 완료된 것으로
읽고 다음 단계로 진행했습니다 — 등록·복구를 중간에 끊은 경우 특히 위험합니다.

이제 명령행 관례대로 `SIGINT` → **`130`**, `SIGTERM` → **`143`** 으로 끝납니다.

중단 시점에 따라 값이 갈리던 것도 함께 맞췄습니다 — 대화형 프롬프트에서 취소하면 이미 `130` 이었고
그 밖에서는 `0` 이었습니다. 이제 어느 쪽이든 같습니다.

> **`exit 0` 에 기대어 Ctrl+C 를 무시하던 스크립트가 있었다면 이제 실패로 잡힙니다.**
> 잘못된 성공 신호가 멈추는 것이므로, 그 스크립트 쪽을 확인하세요.

**표시 변경 — 결과 헤더의 추적 ID**

명령 결과 헤더에 표시되는 식별자가 `requestID` 에서 `traceId` 로 바뀝니다.

- **이전**: `* Recovery Registration Result [requestID: 550e8400-...]`
- **이후**: `* Recovery Registration Result [traceId: a1b2c3d4e5f60718293a4b5c6d7e8f90]`

이 값은 서버 로그의 추적 ID 와 같습니다. 장애 문의 시 함께 전달하면 원인 확인이 빨라집니다.

**동작 변경 — 출력 스트림 분리 (스크립트 작성 시 확인 필요)**

화면에 보이는 모습은 그대로지만, 표준출력(stdout)과 표준에러(stderr)를 무엇으로 채울지가 바뀝니다. 결과를 파이프나 리다이렉트로 받아 처리하고 있었다면 아래 내용을 확인하세요.

- **진행 메시지가 표준에러로 나갑니다.** `* Requesting ...` / `* ... completed (96ms)` 같은 진행 상황 표시가 이제 stderr 로 나갑니다. 화면에 보이는 순서·모습은 같지만 `2> /dev/null` 로 끌 수 있고, 표준출력을 파이프로 넘겨도 결과 데이터에 섞이지 않습니다.
- **`--o json` 의 표준출력이 순수 JSON 이 됩니다.** `zdm-cli ... --o json | jq` 가 그대로 동작합니다. `config show` / `schedule create` 가 JSON 앞에 찍던 설정 파일 경로 같은 평문도 사라졌습니다 (해당 안내는 진행 메시지 쪽, 즉 stderr 로 옮겨갔습니다).
- **색상은 터미널에 출력할 때만 붙습니다.** 결과를 파일로 저장하거나 파이프로 넘기면 ANSI 색상 코드가 섞이지 않습니다. `NO_COLOR` 환경변수를 설정하면 터미널에서도 강제로 끌 수 있습니다.
- **스크립트를 쓰고 계셨다면**: 표준출력에서 진행 메시지를 읽고 있었다면 영향이 있습니다 (이제 stderr 로 나갑니다). **실패 응답 JSON 도 표준에러로 옮겨갔습니다** — 아래 *BREAKING — `--output json` 의 실패 응답* 항목을 반드시 확인하세요. 성공/실패 판별은 (표준출력 내용이 아니라) 종료 코드로 하는 것을 권장합니다.

---

**BREAKING — `--output json` 의 실패 응답이 표준에러로 이동하고 형상이 바뀝니다**

종전에는 성공과 실패의 JSON 형상이 서로 달랐고, 장애 문의에 필요한 `traceId` 가 **정작 실패했을 때만
빠져 있었습니다.** 이제 실패도 성공과 같은 골격을 쓰고, **표준에러(stderr)로** 나갑니다.

```json
{
  "traceId": "a1b2c3d4e5f60718293a4b5c6d7e8f90",
  "success": false,
  "error": {
    "code": "JOB-ERROR-14",
    "message": "...",
    "details": {}
  },
  "timestamp": "2026-09-07T10:30:00.000+09:00"
}
```

- **`error.code` 에 API 의 도메인 에러 코드가 담깁니다.** 종전에는 `HTTP_400` 만 남고 `JOB-ERROR-14`
  같은 값은 버려져서, 에러 메시지 문자열로 분기할 수밖에 없었습니다. 메시지는 언제든 바뀝니다.
- **`traceId` 는 `null` 일 수 있습니다.** 서버에 닿지 못한 실패(접속 불가·타임아웃·설정 누락)에는
  추적 ID 자체가 없습니다.
- 성공 경로의 출력은 바뀌지 않았습니다.

**⚠️ `zdm-cli ... -o json | jq` 로 실패를 파싱하던 스크립트는 빈 입력을 받습니다.**

jq 는 빈 입력에서 오류를 내지 않고 아무것도 출력하지 않은 채 `0` 으로 끝납니다(`-e` 를 붙여도 같습니다).
파이프라인의 `$?` 는 jq 의 것이므로, **실패가 조용히 성공으로 읽힙니다.** 셋 중 하나로 고치세요.

```bash
# 1) pipefail — 파이프라인이 CLI 의 종료 코드를 그대로 반환
set -o pipefail
zdm-cli backup list -o json | jq '.data'

# 2) CLI 자신의 종료 코드를 읽기
zdm-cli backup list -o json | jq '.data'
[ "${PIPESTATUS[0]}" -eq 0 ] || echo "실패"

# 3) 실패 봉투가 필요하면 표준에러로 받기
zdm-cli backup list -o json 2>err.json || sed -n '/^{/,$p' err.json | jq .
```

표준에러에는 사람이 읽는 진단이 먼저 오므로, 3번은 첫 `{` 부터 잘라냅니다.

**BREAKING — `recovery update` 의 `--partition` 폐기**

하나의 원본 파티션을 여러 대상 파티션으로 복구할 수 있게 되면서, 파티션 이름만으로는 어느 복구 단위를
고칠지 특정되지 않습니다. 대상을 **backup image 이름**으로 지목하도록 바뀝니다.

| | v2.0.2 | v3.0.0 |
|---|---|---|
| 옵션 | `--partition` / `-pt` | `--backup-file` / `-bf` (+ `--target-partition` / `-tp`) |

```bash
# 이전
zdm-cli recovery update --id 123 --partition "/" --mode inc

# 이후 — 그 이미지를 쓰는 모든 항목
zdm-cli recovery update --id 123 --backup-file "server01_ROOT_0262.ZIA" --mode inc

# 이후 — 그 항목 하나만
zdm-cli recovery update --id 123 --backup-file "server01_ROOT_0262.ZIA" --target-partition "/data" --mode inc
```

- `--target-partition` 은 OS 를 가리지 않는 단일 옵션입니다 (Linux `/data`, Windows `C:`).
  **종전에는 Windows 용 옵션이 아예 없어 파티션별 수정이 불가능했습니다** — 이번에 함께 해소됩니다.
- 지목할 이미지 이름은 `recovery list` 응답의 백업 파일명에서 확인할 수 있습니다.

---

**BREAKING — `replication monit` 의 `--status` 제거**

`zdm-cli replication monit --status <값>` 이 **파싱 단계에서 즉시 실패**합니다(도움말 출력, 종료 코드 1). 대체 옵션은 없습니다.

이 옵션은 작업 하나를 지목한 뒤 그 작업의 상태가 지정한 값과 다르면 **404** 를 받는 동작이었습니다. 단건 조회에서 404 가 "그 작업이 없다" 와 "있는데 상태가 다르다" 를 뭉개므로 API 에서 제거했고, CLI 도 따라 없앴습니다.

**상태는 응답의 `job.progress.status` 를 읽으면 됩니다** — 조회는 성공하고 상태는 그대로 나옵니다.

`replication list --status` 와 `replication update --status`(작업 시작·중지 지시)는 **영향이 없습니다.**

---

**BREAKING — `replication` · `os-replication` 조회 커맨드의 `--server` 제거**

`replication list` · `replication history` · `replication monit` · `os-replication list` · `os-replication history` 다섯 커맨드에서 `--server` 옵션이 제거됐습니다. 대신 **`--center`** 를 사용하세요.

- `replication` 계열의 작업 정보에는 서버 컬럼 자체가 없습니다. 작업 등록 시 Center 이름이 시스템 이름 컬럼에 들어가므로, `--server` 는 이름과 달리 **실제로는 Center 이름으로 거르는 필터**였습니다. 같은 커맨드의 `--center` 가 Center ID 와 이름을 모두 받고 콤마로 복수 지정까지 되므로 `--server` 가 하던 일을 그대로 대신합니다.
- **스크립트를 쓰고 계셨다면 반드시 고쳐야 합니다.** CLI 는 알 수 없는 옵션을 허용하지 않으므로, `--server` 가 남아 있으면 조용히 무시되는 것이 아니라 **파싱 단계에서 즉시 실패**합니다 — 도움말이 출력되고 종료 코드 1 로 끝나며 요청은 전송되지 않습니다.

```bash
# 이전
zdm-cli replication list --server web01

# 이후 (Center ID 또는 이름, 콤마로 복수 지정 가능)
zdm-cli replication list --center center01
```

`replication regist` 의 `--server` 는 **그대로 유지됩니다.** 이쪽은 `--unit-type server` 로 등록할 때 복제 대상이 되는 실제 서버를 지정하는 파라미터로, 위 조회용 옵션과는 의미가 다릅니다. `backup` · `recovery` 의 `--server` · `--server-name` 도 영향받지 않습니다.

---

**동작 변경 — `recovery monit` 의 서버 기준 조회가 작업 목록으로**

`recovery monit --server-name <이름>` 의 응답이 **작업 목록**이 됩니다. 한 서버는 여러 복구에 원본으로도
대상으로도 걸리므로, 작업 하나만 보여주면 나머지가 가려졌습니다.

- 작업마다 **상태 · 진행률 · 메시지 · 시각 · source/target · 역할(role)** 을 표시합니다.
- 작업 기준 조회(`--job-id`)도 같은 항목을 냅니다 — 두 조회의 출력이 같아집니다.

> **API 와 함께 올려야 합니다.** 짝이 어긋나도 오류는 나지 않고 **값이 비어 보이는 화면**이 되어
> 알아채기 어렵습니다. 구버전 CLI + 신버전 API 는 `[System Information]` 이 비고, `--detail` 의 파티션
> 행이 전부 `-` 로 나옵니다. 신버전 CLI + 구버전 API 도 마찬가지로 작업 단위 값이 비어 보입니다.

---

**동작 변경 — `backup monit` 의 `--log` 와 취소 작업 계수**

- **`--log` 가 쿼리에 반영됩니다.** 종전에는 받아온 로그를 표시할지만 정하는 토글이었는데, API 가 로그를
  상세 응답 전용으로 바꾸면서 이대로 두면 **`--log` 를 켜도 로그가 나오지 않습니다.** 사용법은 그대로입니다.
- **`[Jobs Summary]` 에 `canceled` 가 추가됩니다.** 종전에는 취소된 작업이 어느 버킷에도 잡히지 않아
  합이 `total` 과 맞지 않았습니다. 이 값을 주지 않는 구버전 서버에서는 `0` 으로 표시됩니다.
- `overallProgress` 는 진행 중인 작업이 없을 때 `"0%"` 가 아니라 **`"-"`** 로 나옵니다.

> **서버 기준 조회의 항목 수가 늘 수 있습니다** — 같은 파티션에 작업이 여럿이면 이제 전부 나옵니다
> (종전에는 파티션당 1건). 등록된 작업이 0건이면 오류가 아니라 빈 목록입니다.

---

**수정 — 표 출력에서 숫자 `0` 과 `false` 가 `-` 로 보이던 문제**

`--output table` 에서 **실재하는 `0` 과 `false` 가 값이 없는 것처럼 표시**되고 있었습니다.
사용률 `0%`, 개수 `0`, 꺼져 있는 설정이 전부 `-` 로 나왔습니다.

```
이전: usage 0, enabled false  →  usage "-", enabled "-"
이후: usage 0, enabled false  →  usage 0,   enabled false
```

영향 커맨드: `backup` · `recovery` · `replication` 의 `list` · `history`,
그리고 `license list` · `schedule list` · `server list` · `zdm list` · `file upload`.

> **`-` 를 기준으로 빈 값을 거르던 스크립트는 조건을 고쳐야 합니다.** 이제 그 자리에 `0` 과 `false` 가 옵니다.

---

**수정 — 필드별 검증 오류가 표시되지 않던 문제**

요청 값이 잘못됐을 때 **어떤 필드가 왜 잘못됐는지가 표시되지 않고** 일반 오류 문구만 나오던 문제를 고쳤습니다.

- **이전**: `Request body validation failed.` (어느 필드인지 알 수 없음)
- **이후**: 필드 이름과 사유가 함께 표시됨

API 3.0.0 이 검증 상세의 위치를 바꿨는데 CLI 가 이전 위치만 보고 있어 생긴 문제입니다. 이제 두 위치를 모두 확인하므로 구버전 API 와도 정상 표시됩니다.

---

**복구 등록 시 주의 — 파티션 매핑 규칙 변경**

ZDM-API 3.0.0 부터 **하나의 대상 파티션은 같은 원본 파티션의 이미지를 최대 1장만 받습니다.** 같은 파티션의 이미지 두 장을 한 대상에 지정하면 등록이 거부됩니다.

같은 원본의 이미지를 여러 장 쓰려면 서로 다른 대상 파티션에 1장씩 배정하세요. 이 배치는 3.0.0 부터 허용됩니다.
