<summary><strong>v2.0.2</strong> — Delete 응답 양식 통일 (BREAKING) / Backup-Update Schedule 변경 detail 구조 확장</summary>

사용자 가이드(엔드포인트·요청/응답 스키마) 변경 2건. **응답 양식 BREAKING 변경 포함** — 기존 응답 구조에 의존하는 클라이언트는 코드 수정 필요.

**BREAKING — Replication / OS Replication Delete 응답 양식 통일**

- `DELETE /replications/:identifier`, `DELETE /os-replications/:identifier` 응답 본문 구조가 backup/recovery 와 동일한 `jobInfo[] + summary` 구조로 교체됨
- **이전**: `{ deletedJob: { id, name }, deletedRelations: { replicationInfo, history, logEvent } }`
- **이후**: `{ jobInfo: [{ name, deletedComponents: {basicInfo, detailInfo, historyData, logData} }], summary: { state, affectedComponents: {basicInfoDeleted, detailInfoDeleted, historyDataDeleted, logDataDeleted} } }`
- 자세한 매핑은 [DELETE /replications/:identifier](../docs/replication/delete) 및 [DELETE /os-replications/:identifier](../docs/os-replication/delete) 참조. 이전 양식은 각 페이지의 `delete/2.0.1.md` 참고

| 도메인 4개 테이블 | 통일 후 키 |
|---|---|
| Main (active_replication / Main) | `summary.affectedComponents.basicInfoDeleted` (항상 1) |
| Info (job_replication_info) | `summary.affectedComponents.detailInfoDeleted` |
| History | `summary.affectedComponents.historyDataDeleted` |
| LogEvent | `summary.affectedComponents.logDataDeleted` |

- **의미 차이 명시**:
  - replication / os-replication 은 atomic transaction → `state` 는 응답 본문이 만들어지면 항상 `"success"` (실패 시 throw → 404/500). backup/recovery 는 `Promise.allSettled` 라 `"fail"` 케이스 가능
  - `partition` 키 부재 (replication 은 partition 개념 없음)
  - `errorMessage` 키 부재 (atomic 이라 부분 실패 경로 없음)
  - 기존 `deletedJob.id` 정보 제거됨 (backup 응답에도 id 없음 — name 만)

**Schema Extension — Backup Update 응답 Schedule 변경 detail 구조 확장**

- `PUT /backups/:identifier` 응답의 `summary.updatedFields[]` 중 **Schedule 계열** 필드 (`Schedule` / `Schedule(Basic)` / `Schedule(Advanced)`) 의 `previous` / `new` 가 단순 ID 가 아닌 `{ id, type, description }` 객체로 확장
- **이전**: `{ "field": "Schedule", "previous": 5, "new": 10 }`
- **이후**: `{ "field": "Schedule", "previous": { "id": 5, "type": "daily", "description": "매일 03:00 실행" }, "new": { "id": 10, "type": "daily", "description": "매일 03:00 실행" } }`
- 사용자가 schedule id 만 보낸 경우의 자동 복제 (1 schedule = 1 job 원칙) 시 `notices` 에 안내 메시지 첨부: `"Schedule was duplicated (1 schedule = 1 job principle). Source schedule ID: N, new schedule ID: M."`
- 그 외 필드 (`jobName`, `mode`, `rotation`, `compression`, `repository`, `path` 등) 의 `previous` / `new` 응답 형식은 변경 없음 (기존 단순 값 유지)
- 이전 양식은 [PUT /backups/:identifier v2.0.1](../docs/backup/update/2.0.1.md) 참고

**ScheduleChangeValue 구조** (v2.0.2 신규)

| 필드 | 타입 | 설명 |
|------|------|------|
| `id` | number | schedule ID |
| `type` | string | lowercase short alias (`daily`, `weekly`, `monthly_date`, `smart_weekly`, `smart_monthly_week`, `smart_monthly_date`, `smart_custom_monthly_week`, `smart_custom_monthly_date`, `once`, `every_minute`, `hourly`, `unknown`) |
| `description` | string | schedule 내용 한국어 설명 (조회 실패 시 `"스케줄 조회 실패"`) |

> id ≤ 0 (이전 schedule 없음 / 모드 전환 reset) 인 경우 해당 필드는 `null` 로 반환됩니다.

**클라이언트 영향도 요약**

| 변경 | 영향 | 권장 대응 |
|---|---|---|
| Replication Delete 응답 | **BREAKING** | 응답 파싱 코드 갱신 (jobInfo[] + summary 구조로) |
| OS Replication Delete 응답 | **BREAKING** | 동일 |
| Backup Update — Schedule 변경 detail 객체화 | 부가적 (기존 number 비교 코드는 type 분기 필요) | `typeof previous === "object" ? previous.id : previous` 패턴 |
| Backup Update — Schedule 외 필드 | 변경 없음 | — |
| Backup Update — notices 신규 필드 | 부가적 | 사용 시 표시 |

**운영 개선 (사용자 영향 없음)**

- zdm-api 내부 아키텍처 정비 (Modular Monolith + DDD-lite 3계층 통일, port/adapter 패턴 폐기, `infrastructure/persistence` 디렉토리 단순화 `repository`, dependency-cruiser 도입 등) — **외부 API 응답·요청 스키마 변경 없음 (위 2건 외)**
- zdm-cli v2 동기화 — 위 응답 양식 변경 대응
