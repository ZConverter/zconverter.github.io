사용자 가이드(엔드포인트·요청/응답 스키마) 변경 다수. **응답 양식 BREAKING 변경 포함** — 기존 응답 구조에 의존하는 클라이언트는 코드 수정 필요.

**BREAKING — Replication / OS Replication Delete 응답 양식 통일**

- `DELETE /replications/:identifier`, `DELETE /os-replications/:identifier` 응답 본문 구조가 backup/recovery 와 동일한 `jobInfo[] + summary` 구조로 교체됨
- **이전**: `{ deletedJob: { id, name }, deletedRelations: { replicationInfo, history, logEvent } }`
- **이후**: `{ jobInfo: [{ name, deletedComponents: {basicInfo, detailInfo, historyData, logData} }], summary: { state, affectedComponents: {basicInfoDeleted, detailInfoDeleted, historyDataDeleted, logDataDeleted} } }`
- 자세한 매핑은 [DELETE /replications/:identifier](/zdm/ko/api/2.0.2/docs/replication/delete) 및 [DELETE /os-replications/:identifier](/zdm/ko/api/2.0.2/docs/os-replication/delete) 참조. 이전 양식은 v2.0.0 문서([replication](/zdm/ko/api/2.0.0/docs/replication/delete) · [os-replication](/zdm/ko/api/2.0.0/docs/os-replication/delete)) 참고

| 도메인 4개 테이블 | 통일 후 키 |
|---|---|
| Main (active_replication / Main) | `summary.affectedComponents.basicInfoDeleted` (항상 1) |
| Info (job_replication_info) | `summary.affectedComponents.detailInfoDeleted` |
| History | `summary.affectedComponents.historyDataDeleted` |
| LogEvent | `summary.affectedComponents.logDataDeleted` |

- **의미 차이 명시**:
  - replication / os-replication 은 atomic transaction → `state` 는 응답 본문이 만들어지면 항상 `"success"` (실패 시 throw → 404/500). backup/recovery 는 `Promise.allSettled` 라 `"fail"` 케이스 가능
  - `partition` 키 부재 (replication 은 partition 개념 없음)
  - `errorMessage` 키 부재 (atomic 이라 부분 실패 경로 없음)
  - 기존 `deletedJob.id` 정보 제거됨 (backup 응답에도 id 없음 — name 만)

**Schema Extension — Schedule 응답 형식 4 도메인 통일 (`{ id, type, description }`)**

backup / recovery / replication / os-replication 의 schedule 응답 형식을 단일 진실원 (`schedule-describer.utils.ts`) 으로 통일. 5 endpoint(`POST /backups`, `POST /recoveries`, `POST /replications`, `POST /os-replications`, `PUT /backups/:id` / `PUT /replications/:id` / `PUT /os-replications/:id` 의 Schedule 변경 detail)에 동일 객체 형식 적용.

**ScheduleDescribeValue 구조** (v2.0.2 신규)

| 필드 | 타입 | 설명 |
|------|------|------|
| `id` | number | schedule ID |
| `type` | string | `ScheduleTypes.Type.Map.toString` 결과 (PascalCase 영문 — `"Daily"`, `"Weekly"`, `"Smart Weekly (Specific Day of the Week)"` 등) |
| `description` | string | `processScheduleInfo` 결과 (영문 — `[Basic]` / `[Advanced]` prefix 포함). 조회 실패 시 `"Schedule lookup failed"` |

> schedule id ≤ 0 (이전 schedule 없음 / 모드 전환 reset / 미지정) 인 경우 해당 필드는 `"-"` placeholder 또는 응답에서 제외됩니다.

**도메인별 응답 위치**

| Endpoint | 응답 경로 | 변경 |
|---|---|---|
| `POST /backups` | `results[].schedule.basic` / `advanced` | `{ type, description }` → `{ id, type, description }` ( `id` 신규 추가 ) |
| `POST /recoveries` | `common.schedule.basic` | `{ type, description }` → `{ id, type, description }` |
| `POST /replications` | `results[].schedule` | **신규 노출** (이전 응답에 schedule 정보 부재) — `{ id, type, description }` |
| `POST /os-replications` | `results[].schedule` | **신규 노출** (이전엔 schema 에만 정의되어 있고 service 가 무시) — `{ id, type, description }` |
| `PUT /backups/:id` | `summary.updatedFields[].previous` / `new` | 단순 ID → `{ id, type, description }` (Schedule 계열 필드만) |
| `PUT /replications/:id` | `summary.updatedFields[].previous` / `new` (Schedule 변경 시) | **신규 노출** — `{ id, type, description }` |
| `PUT /os-replications/:id` | `summary.updatedFields[].previous` / `new` (Schedule 변경 시) | **신규 노출** — `{ id, type, description }` |

**예시 — backup-update 의 Schedule 변경 detail**

```json
// 이전
{ "field": "Schedule", "previous": 5, "new": 10 }

// 이후
{
  "field": "Schedule",
  "previous": { "id": 5, "type": "Daily", "description": "[Basic] Start working at 03:00 every day." },
  "new":      { "id": 10, "type": "Daily", "description": "[Basic] Start working at 03:00 every day." }
}
```

**클라이언트 영향도**

| 변경 | 영향 | 권장 대응 |
|---|---|---|
| 응답에 `schedule.id` 신규 노출 | 부가적 | 새 필드 활용 가능 (이전엔 id 미포함) |
| Schedule 객체 → `{ id, type, description }` | 부가적 | 기존 number 비교 코드는 type 분기 필요: `typeof previous === "object" ? previous.id : previous` |
| 다른 필드 (jobName, mode 등) | 변경 없음 | — |

**New Feature — Replication / OS-Replication 작업의 schedule 처리 신설**

`POST /replications` / `PUT /replications/:id` + `POST /os-replications` / `PUT /os-replications/:id` 의 body schema 에 정의되어 있던 `schedule` 필드가 그동안 service 에서 무시되던 문제 해결. backup/recovery 와 동일한 흐름으로 schedule 검증·등록·응답 노출.

- **신규 동작**: `schedule` 입력 시 검증 후 `job_replication.nScheduleID` / `job_os_replication.nScheduleID` 저장 + 응답 `schedule: { id, type, description }` 노출. 정기 동작 정상.
- **지원 범위**: basic schedule 만 (DB nScheduleID 단일 컬럼). smart schedule 입력 시 `INVALID_SCHEDULE_JOB_MODE_FOR_BASIC` 400 응답.
- **jobMode**:
  - replication: `full` / `increment` / `sync` 모두 schedule 허용
  - os-replication: `full` / `increment` (sync 미지원)
- **회귀 영향**: schedule 미지정 시 동작 100% 동일 (`nScheduleID = 0`)
- **4 도메인 일관성**: backup / recovery / replication / os-replication 모두 동일 schedule 처리 + 응답 형식

**New Feature — Recovery 등록 시 backup 없는 partition 자동 skip**

`POST /recoveries` 호출 시 source 서버의 partition 중 backup 작업·이미지가 없는 partition 은 자동으로 jobList 에서 제외. `excludePartition` 옵션 미지정 케이스에서도 동작.

- **신규 동작**: backup 없는 partition 은 silent skip + 응답 `notices` 필드에 안내 메시지 (`"Partition/drive 'D:' was skipped — no backup available: ..."`)
- **전체 skip 시**: 모든 partition 에 backup 없으면 `JOB-ERROR-01` (NOT_FOUND) 명확한 메시지로 throw
- **silent skip 대상**: `Job.Common.NOT_FOUND` 만. BAD_REQUEST (예: backupFile-partition mismatch) / 다른 도메인의 NOT_FOUND (예: ZDM_REPOSITORY-NOT-FOUND) 는 그대로 throw 하여 사용자가 인지
- **listOnly 정책**: `true` / `false` 모두 동일 적용 (CLI/API 사용자 편의)

**시나리오 예시** — Windows source `C/D/E` 중 `C` 만 backup, target `C/D`:
```json
// 이전: 전체 등록 실패 (D, E 의 backup 없음 에러)
// 이후 (변경): C 만 정상 등록 + notices 안내
{
  "results": [ /* C drive 정상 등록 결과 */ ],
  "notices": [
    "Partition/drive 'D:' was skipped — no backup available: Backup job not found for partition 'D:' on server 'src-win01'",
    "Partition/drive 'E:' was skipped — no backup available: Backup job not found for partition 'E:' on server 'src-win01'"
  ]
}
```

**Bugfix — Backup/Recovery Update 의 Status diff `previous` 값 정확화**

`PUT /backups/:id` / `PUT /recoveries/:id` 응답의 `updatedFields[]` 중 **Job Status 변경 detail** 의 `previous` 값이 UI 와 일치하도록 정정.

- **이전 버그**: `previous` 가 DB `nJobStatus` 컬럼 raw 값 ("Complete") 그대로 표시되어, 사용자가 UI 에서 보는 작업 상태 ("Registered") 와 어긋남
- **이후**: `previous` 가 `calculateJobStatus()` 결과 ("Registered" / "Processing" / "Scheduled" / ...) 로 UI 와 일치
- **`current` 값 정책**: 사용자가 요청 body 로 보낸 status 문자열 그대로 echo (active 우선 규칙으로 인한 혼동 회피)
- **예시**:
  ```json
  // 작업이 UI 에서 "Registered" 로 표시 + 사용자가 status: "start" 요청
  // 이전: { "previous": "Complete", "new": "Start" }
  // 이후: { "previous": "Registered", "new": "start" }
  ```

**Security — 인증·인가 강화**

- **`GET /users/:identifier` / `PUT /users/:identifier` — 본인 리소스만 접근 허용**
  - 토큰 주체(user id 또는 email)와 `:identifier` 가 불일치하면 **403 Forbidden** — `You can only access your own user resource.`
  - email 비교는 대소문자를 구분하지 않습니다. path parameter 검증(400)이 먼저 평가됩니다
  - `GET /users` (전체 목록)은 이번 버전의 적용 대상이 아닙니다
- **`POST /token/issue` — 요청 횟수 제한 신설**
  - IP 기준 슬라이딩 윈도우 초과 시 **429 Too Many Requests** (`RATE-LIMIT-01`). 기본값 15분당 20회
- **`GET /cloud-auth/regions/:platform` — 지원 platform 화이트리스트 검증**
  - `aws` / `gcp` 외의 값은 파일 접근 이전에 **400 Bad Request** — `Unsupported platform: <platform>. Supported platforms: aws, gcp`
- **`GET /files/download/:fileName` / `GET /cloud-auth/zos/download/:fileName` — 경로 이탈 차단**
  - 파일명에 `..` 또는 절대경로가 포함되어 기준 디렉토리를 벗어나면 **400** (`FILE-ERROR-11`)

**신규 에러코드**

| 코드 | HTTP | 메시지 | 발생 시점 |
|---|---|---|---|
| `FILE-ERROR-11` | 400 | Invalid file path. | 요청한 파일명이 기준 디렉토리를 벗어나는 경우 |
| `RATE-LIMIT-01` | 429 | Too many authentication attempts. Please try again later. | 토큰 발급 요청 횟수 초과 |

**Schema Extension — `PUT /backups/:identifier`**

- **`repository.id` 필수 → 선택 완화**: `id` 를 생략하면 기존 repository 를 유지한 채 `path` 만 변경할 수 있습니다.
  등록 흐름(`POST /backups`)의 `repository.id` 는 기존대로 필수입니다
- **응답 `notices?: string[]` 신규**: schedule 을 ID 로만 지정한 경우 처리 결과 안내 메시지가 담깁니다. 값이 없으면 응답에서 생략됩니다
