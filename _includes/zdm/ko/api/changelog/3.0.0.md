**동작 변경 — `GET /zdms` 의 `detail=true` 가 `resources` 를 반환**

`detail` 파라미터는 종전까지 **받아들여지기만 하고 응답을 바꾸지 않았습니다.** 이제 하드웨어·시스템
정보인 `resources` 블록을 반환합니다. 위치는 `path` 다음, 부가 정보 배열 앞입니다.

```json
"resources": {
  "model": "PowerEdge R740",
  "cpu": "Intel(R) Xeon(R) Gold 6248",
  "cpuCount": "2",
  "memory": "34359738368 (32.00 GB)",
  "kernel": "5.15.0-91-generic",
  "systemType": "x86_64",
  "organization": "ZConverter"
}
```

- `memory` 는 `원값 (읽기 쉬운 값)` 형식입니다. 원값이 바이트 숫자가 아니면 그 값을 그대로 냅니다.
- 값이 없는 항목은 `"-"` 입니다.
- 목록 · 페이지네이션 · 단건 조회 세 경로 모두 동일하게 동작합니다.

`detail` 을 보내지 않는 요청의 응답은 종전과 같습니다.

자세한 내용은 [ZDM 목록 조회](/zdm/ko/api/3.0.0/docs/zdm/list) 참조.

**BREAKING — 파일 업로드 응답의 `path` 가 다운로드 URL 로**

`POST /files/upload` 응답의 `path` 가 **서버 파일시스템 절대경로**였습니다. 원격 클라이언트가 쓸 수 없는
값인 데다 서버 내부 구조가 드러났고, 환경에 따라 값의 모양도 달랐습니다.

```diff
-  "path": "/ZConverterManager/api-files/uploads/file-1757222400000-123456789-report.xlsx"
+  "path": "/api/files/download/file-1757222400000-123456789-report.xlsx"
```

- 필드 이름·개수·타입은 그대로입니다. 값만 **바로 내려받을 수 있는 URL** 로 바뀝니다.
- 파일명은 URL 인코딩됩니다 — 공백이나 한글이 든 파일명에서도 링크가 끊기지 않습니다.
- 목록 응답(`GET /files`)은 종전부터 경로를 노출하지 않았습니다. 업로드만 달랐던 것을 맞춘 것입니다.

**업로드 응답의 `path` 를 파일시스템 경로로 쓰던 코드가 있으면 고쳐야 합니다.**

**동작 변경 — `GET /zdms` 의 `?zosRepository=true` 가 실제 값을 반환**

이 파라미터는 **받아들여지기만 하고 언제나 빈 배열을 반환**했습니다. ZOS 저장소가 실재해도 응답은
`"zosRepository": []` 라서 **"없음" 으로 오독되는 값**이 나갔습니다. 이제 실제 값이 담깁니다.

```json
"zosRepository": [
  {
    "id": "3",
    "centerName": "Main-Center",
    "size": "10TB",
    "platform": "aws",
    "cloudKeyId": "key-01",
    "bucketName": "zdm-backup",
    "created": "2025-01-10 09:00:00",
    "lastUpdated": "2025-01-15 10:30:00"
  }
]
```

`zosRepository=true` 를 주지 않는 요청은 종전대로 빈 배열입니다 — **기존 연동에는 변화가 없습니다.**

**동작 변경 — 복구 등록이 한 번도 실행되지 않은 백업을 거부**

백업 작업이 **등록만 되고 한 번도 실행되지 않았는데도** 복구 등록에서 "사용 가능" 으로 판정됐습니다.
실제 이미지 파일이 없으므로 복구는 실패할 수밖에 없는데, 등록은 성공하던 상태였습니다.

이제 실행 이력이 없는 백업은 복구 등록에서 거부됩니다. **한 번이라도 실행된 백업이면 종전과 같습니다.**

**수정 — 받아들여지지만 동작하지 않던 필터 4건**

스키마가 값을 받고 검증까지 하는데 **실제로는 결과를 좁히지 않던** 파라미터들입니다. 요청은 성공했으므로
"필터가 적용됐다" 고 믿을 근거만 있고 결과는 필터 없는 것과 같았습니다.

| 대상 | 종전 동작 |
|---|---|
| `GET /servers/{identifier}/partitions` 의 `center` | 서버를 찾을 때 쓰이지 않아, **동명 서버가 있으면 다른 center 의 파티션**이 나갔습니다 |
| `GET /zdm/{identifier}/repositories` 의 `center` | 조건이 충돌해 **항상 0건** 이었습니다 |
| `GET /licenses` 의 `sort=asc` | 값이 전달되지 않아 **언제나 내림차순** 이었습니다 |
| `GET /files` 의 `sort` | 정렬 코드가 없어 **디렉터리 읽기 순서** 그대로 나갔습니다 |

파일 목록은 같은 시각이면 파일명으로 갈라 순서를 확정합니다 — 페이지네이션이 요청마다 흔들리지 않게 하기
위해서입니다.

**수정 — 삭제·조회가 다른 center 의 동명 리소스에 닿던 문제**

서버·작업 이름은 **center 간 유일하지 않습니다.** 이름만으로 행을 지목하던 자리들이 다른 center 의
동명 리소스에 닿고 있었습니다.

- **`DELETE /servers/{identifier}`** — `id` 로 지목해도 부속 정보(디스크·네트워크·파티션·저장소)는
  **이름으로 지워졌습니다.** 다른 center 에 동명 서버가 있으면 그 서버의 부속 행이 함께 사라져
  "부속 정보가 빈 서버" 가 남았습니다.
- **`center` 를 지정한 서버 조회·삭제** — 그 center 안에서 서버를 찾습니다. 종전에는 임의의 첫 행을
  집고 나서 소속을 대조해, **요청한 center 에 서버가 실존해도 거절**되는 경우가 있었습니다.
  "다른 center 에 있다"(403)와 "아예 없다"(404)의 구분은 그대로입니다.
- **center 삭제 · 작업 이름 변경 전파 · os-replication 삭제** 도 같은 방식으로 범위를 좁혔습니다.

**에러 코드 계약은 바뀌지 않았습니다.**

**BREAKING — `GET /backups/images` 의 `serverName` 파라미터가 `server` 로**

`center` 는 ID 와 이름을 한 파라미터로 받고 `centerName` 이라는 파라미터가 없습니다. `server` 도 다른
12곳에서 같은 규칙인데 이 엔드포인트만 `serverName`(이름 전용)으로 어긋나 있었습니다.

| | v2.0.2 | v3.0.0 |
|---|---|---|
| 파라미터 | `serverName` (이름만) | **`server`** (ID 또는 이름) |

**⚠️ 실패가 400 이 아니라 조용한 오답입니다.** 이 엔드포인트의 쿼리 스키마는 모르는 키를 조용히
버리므로, `?serverName=web01` 을 보내면 **에러 없이 그 키가 사라지고 필터가 걸리지 않은 전체 목록이
`200` 으로** 나갑니다. 배포 짝이 어긋나도 마찬가지입니다 — 확인 없이는 알아채기 어렵습니다.

- **ID 로도 조회됩니다.** 숫자를 주면 서버 이름을 찾아 대조합니다.
- ID 로 서버를 찾지 못해도 `404` 가 아니라 **0건**입니다 — source 서버가 삭제된 뒤에도 이미지는 남아
  있고, 그 이미지는 이름으로만 조회할 수 있기 때문입니다.

CLI 는 종전부터 `--server` 로 노출했으므로 **CLI 사용자에게는 체감 변화가 없습니다.**

**수정 — 진행 중이거나 실패한 작업이 완료로 보고되던 문제**

복구가 끝난 뒤 **재부팅 이전 단계**의 작업이 API 응답에서 `Complete` 로 나갔습니다. 웹 화면은 같은 작업을
`Processing` 으로 표시했고, 웹이 맞았습니다.

복구의 진행 행은 **파티션마다 하나씩** 있고, 그중 종료 단계 행은 "그 파티션의 복사가 끝났다" 는 뜻입니다 —
작업 전체의 종료가 아닙니다. 그런데 첫 행이 종료 단계면 작업 전체가 완료로 판정됐습니다.

이제 **종료 단계 행이 있어도 작업 본체가 진행 중이라고 말하면 완료를 선언하지 않습니다.**
함께 고친 것:

- 실패한 작업이 완료로 보고되던 경로
- 이미 끝난 작업의 진행 행이 남아 있을 때 진행 중으로 보이던 문제 (재실행 직후 포함)

**모니터링 응답의 상태 값이 달라질 수 있습니다.** 종전에 `Complete` 로 보이던 작업이 실제 상태
(`Processing` · 실패)로 나옵니다.

---

**수정 — `detail=true` 모니터링이 지난 실행의 로그를 반환하던 문제**

백업·복구 모니터링의 `detail=true` 가 **최신 실행이 아니라 지난 실행의 로그**를 반환할 수 있었습니다.
로그 행의 조회 순서에 따라 최신 실행 그룹을 잘못 고르는 경로가 있었습니다.

이제 조회 순서와 무관하게 최신 실행을 고릅니다. **로그를 보고 현재 진행을 판단하던 화면에서
값이 달라질 수 있습니다** — 종전에 지난 실행의 내용이 보이던 자리에 이번 실행의 내용이 옵니다.

**BREAKING — `error` 가 문자열에서 객체로**

에러 응답의 `error` 필드가 문자열에서 `{ code, message, details? }` 객체로 바뀝니다.

- **이전**: `"error": "Specified partition does not exist on the server."`
- **이후**: `"error": { "code": "JOB-ERROR-13", "message": "Specified partition does not exist on the server." }`

`error.code` 는 안정 식별자입니다. **클라이언트는 메시지 문자열이 아니라 이 값으로 분기하세요** — 메시지 문구는 예고 없이 바뀝니다. 전체 목록은 [에러 코드](/zdm/ko/api/3.0.0/docs/error-codes) 참조.

기존 최상위 `detail.validationErrors` 는 **`error.details` 로 흡수**됩니다. 검증 실패일 때만 응답 모양이 달라지던 변형이 사라지고 모든 에러가 한 형태가 됩니다.

```json
{
  "success": false,
  "traceId": "a1b2c3d4e5f60718293a4b5c6d7e8f90",
  "error": {
    "code": "DTO-VALIDATION-01",
    "message": "Request body validation failed.",
    "details": { "center": ["center is required"] }
  },
  "timestamp": "2026-08-28T10:30:00.000+09:00"
}
```

**BREAKING — `requestID` 가 `traceId` 로**

응답 본문의 `requestID` 키 이름이 `traceId` 로 바뀝니다. **성공 응답에도 적용됩니다.**

값은 그대로이며, 응답 헤더 `X-Trace-Id` · 서버 로그의 `traceId` 와 **완전히 같은 값**입니다. 장애 문의 시 이 값을 전달하면 서버 로그를 바로 찾을 수 있습니다.

**BREAKING — 복구 모니터링 응답이 작업 목록으로**

`GET /recoveries/monitoring/system/:identifier` 가 서버에 걸린 복구 작업을 **전부** 반환합니다.

- **이전**: `{ system, job }` — 작업 **1건**만
- **이후**: `{ server, summary, job }` — `job` 이 **배열**

이전에는 최신 1건만 나와, 하나의 source 서버 이미지로 여러 대상 서버에 동시에 복구를 걸면 **나머지 작업이 보이지 않았습니다.** 최상위 `system` 키는 사라지고, 원본·대상 서버는 각 작업의 `info.source` · `info.target` 에 담깁니다.

`summary` 가 새로 담깁니다 — 상태별 작업 수와 `total`, 전체 진행률입니다. **상태 버킷의 합은 항상 `total` 과 같습니다.**

`GET /recoveries/monitoring/job/:identifier` 는 단건 그대로이며, **작업 객체의 구조가 서버 기준 조회와 같아집니다.** 두 경로를 같은 코드로 파싱할 수 있습니다.

자세한 내용은 [서버 기준 모니터링](/zdm/ko/api/3.0.0/docs/recovery/monitoring-system) · [작업 기준 모니터링](/zdm/ko/api/3.0.0/docs/recovery/monitoring-job) 참조.

**BREAKING — 복구 모니터링 응답이 `progress` 로 묶이고 파티션별 진행률이 기본 응답으로**

작업 객체에 평면으로 놓여 있던 `status` · `percent` · `message` 가 **`job.progress` 안으로** 들어가고, `details[]` 가 **`progress.partitions[]`** 로 바뀝니다. 두 모니터링 경로 모두 해당합니다.

```
job
├─ info      { id, name, source, target, role? }
├─ progress  { status, percent, message, partitions[] }
├─ timeInfo  { start, elapsed, end }
└─ log[]                                    ← detail=true · 작업 기준 조회 전용
```

| | v2.0.2 | v3.0.0 |
|---|---|---|
| 작업 상태 · 진행률 · 메시지 | `job.status` · `job.percent` · `job.message` | **`job.progress.status` · `.percent` · `.message`** |
| 파티션/드라이브 배열 | `job.details[]` | **`job.progress.partitions[]`** |
| 파티션 이름(`partition`/`drive`) · `backupFile` | `detail=true` | **기본 응답** |
| 파티션별 `status` · `percent` · `message` · `timeInfo` | `detail=true` | **기본 응답** |
| `targetDisk` · `size` · `mode` · `diskNumber` · `overwrite` | `detail=true` | `detail=true` |
| 작업 로그 `log` | `detail=true` (작업 기준 조회 전용) | `detail=true` (작업 기준 조회 전용) |

**파티션별 진행률이 기본 응답으로 올라옵니다.** 모니터링 화면이 실제로 원하는 값이 플래그 뒤에 있었습니다. 이제 `detail` 없이 폴링하면서 파티션별 진행률 막대를 그릴 수 있습니다. `progress.partitions` 키는 `detail` 과 무관하게 **항상 있으며**, 필터에 맞는 행이 없으면 빈 배열입니다.

**`detail=true` 가 담당하는 것은 파티션 메타데이터와 작업 로그입니다.** 대상 디스크·크기·복구 방식·디스크 번호·덮어쓰기 설정은 폴링 중에 바뀌지 않는 값이라 매 호출 실어 보낼 이유가 없습니다 — 파티션이 많은 서버일수록 페이로드 크기 차이가 큽니다.

**파티션 `message` 는 작업명 접두어가 제거된 형태입니다.** 작업 단위 `progress.message` 는 데몬이 기록한 원문 그대로(`[source-server_home] 62%, Processed Size: 5.680 MB | Speed: 36.83 MB/s`)이고, 파티션 행의 `message` 는 앞의 `[...]` 를 뗀 형태(`Processed Size: 5.680 MB | Speed: 36.83 MB/s`)입니다. 파티션 객체 안에서 작업명은 중복이기 때문입니다.

파티션 원소 안에서 진행 값을 다시 감싸지 않습니다 — `status` · `percent` · `message` · `timeInfo` 가 행에 **평탄하게** 실립니다. Windows 는 `partition` 대신 **`drive` 키**를 쓰며 이는 종전과 같습니다.

서버 기준 조회의 `data.server` · `summary` · `job[]` 최상위 구조와 `info.role` 은 그대로입니다. **`detail=true` 여도 `log` 는 실리지 않습니다** — 작업 수만큼 로그를 읽게 되므로 현행 정책을 유지합니다.

**BREAKING — 복구 모니터링의 `detail` 과 필터**

`detail` 이 실제로 동작합니다. **`detail` 없이 호출하면 파티션 메타데이터와 `log` 키가 응답에 없습니다** — 목록·상태 갱신용 경량 응답입니다. 파티션별 진행률은 위 항목대로 기본 응답에 실리므로, 상세 화면에서 디스크 구성이나 로그가 필요할 때만 `detail=true` 로 호출하세요.

작업 진행 메시지가 **작업 단위 `progress.message` 로 올라옵니다.** 이전에는 상세를 받지 않으면 메시지를 볼 수 없었습니다.

**`progress.partitions[]` 의 각 행이 그 파티션의 실제 진행을 담습니다.** 이전에는 작업 단위 값을 행마다 그대로 복사해, 파티션이 셋이면 셋 다 같은 상태·같은 진행률로 보였습니다. 이제 각 행이 자기 파티션의 `status` · `percent` · `message` · `timeInfo` 를 냅니다 — 한 작업 안에서 어떤 파티션은 끝나고 어떤 파티션은 아직 시작하지 않은 것이 정상입니다. **아직 시작하지 않은 파티션은 `status` 가 `Registered` 이고 `percent` · `message` · `timeInfo` 가 모두 `"-"`** 입니다 (`0%` 가 아닙니다 — 시작하지 않은 것과 시작해서 0% 인 것은 다릅니다).

중첩 객체 `progressInfo` 는 사라지고 네 값이 행에 **평탄하게** 실립니다. 각 행에는 `backupFile` 도 함께 담깁니다 — 같은 파티션이 여러 행으로 보일 때 어느 이미지에서 온 행인지 구분됩니다. 이 값들은 모두 기본 응답에 있습니다.

한 응답의 `progress.partitions[]` 세 행이 어떻게 달라지는지 (아래 열은 모두 **기본 응답**에 실립니다):

| `partition` | `backupFile` | `status` | `percent` | `message` | `timeInfo.end` |
|---|---|---|---|---|---|
| `/` | `daily-backup_…ZIA` | `Complete` | `"100%"` | `Recovery completed.` | `2025-01-15 10:36:25` |
| `/home` | `daily-backup_…ZIA` | `Processing` | `"62%"` | `Processed Size: 5.680 MB …` | `"-"` |
| `/home` | `weekly-backup_…ZIA` | `Registered` | `"-"` | `"-"` | `"-"` |

**작업 단위 `percent` 와 `summary.overallProgress` 의 출처가 바뀌었습니다.** 데몬이 세어 둔 복구 완료 개수에서 나옵니다 — 이전에는 진행 행의 평균이었습니다. **`progress.partitions[]` 로 이 값을 다시 계산하지 마세요.** 행의 진행률을 평균 내거나 완료된 행 수를 세도 같은 값이 되지 않습니다. 위 예시도 3행 중 1행이 완료(33%)지만 작업 진행률은 `"45%"` 입니다. 응답의 값을 그대로 표시하세요.

**로그는 작업 기준 조회의 `detail=true` 에서만** 반환됩니다. 서버 기준 조회는 `detail=true` 여도 로그를 담지 않습니다.

제거된 쿼리 파라미터:

| 파라미터 | 경로 | 사유 |
|---|---|---|
| `sort` | 양쪽 | 진행 중 작업이 항상 앞에 옵니다 |
| `server` | 양쪽 | 경로에 이미 있습니다 |
| `status` · `serverType` · `jobName` | 작업 기준 | 경로가 작업을 이미 지목했습니다 (상태는 응답의 `job.progress.status` 로 읽습니다) |

**이 값들은 더 이상 받지 않습니다** — 요청에 실으면 `400` (`DTO-VALIDATION-03`) 이고 `error.details` 에 해당 파라미터 이름이 담깁니다. 종전에는 조용히 무시됐습니다.

`status` 필터(서버 기준)는 이제 **목록을 거릅니다.** 이전에는 작업 1건을 고른 뒤 상태가 맞지 않으면 404 였습니다 — 조건에 맞는 다른 작업이 있어도 그랬습니다. **조건에 맞는 작업이 없으면 200 에 빈 배열**이며, 404 는 서버나 작업이 실제로 없을 때만입니다.

`page` · `limit` 을 서버 기준 조회에서 쓸 수 있습니다. **`summary` 는 필터를 통과한 전체 기준이고 `job` 은 그 중 한 페이지**이므로, 페이지 범위를 넘기면 `job` 이 빈 배열이면서 `summary.total` 이 0보다 큰 것이 정상입니다.

**BREAKING — Windows 복구 등록의 `overwrite` 가 에러 대신 무시**

`overwrite` 는 대상 서버에 짝이 없는 데이터 파티션을 `/` 로 통합하는 **Linux 규칙**입니다. Windows 는 드라이브 단위라 통합할 상위 대상이 없어 이 옵션이 애초에 아무 동작도 하지 않습니다. 그럼에도 v2.0.2 까지는 Windows 대상에 `overwrite: "allow"` 가 오면 등록 전체를 거부했습니다.

| 요청 | v2.0.2 | v3.0.0 |
|---|---|---|
| Windows 대상 + `overwrite: "allow"` (전역 또는 `jobList[].overwrite`) | `JOB-ERROR-56` (409) 거부 | **등록 성공.** 옵션만 무시 + `notices` 안내 |
| Linux 대상 + 전역 `overwrite: "allow"` | 허용 | 허용 |

**함께 고쳐진 것 — Linux 의 `jobList[].overwrite`**: 검증이 OS 를 가리지 않고 있어 **Linux 대상에서도 `jobList[].overwrite: "allow"` 가 `JOB-ERROR-56` 으로 거부**되고 있었습니다. 파티션마다 다른 `overwrite` 를 주려면 전역 `overwrite` 를 쓸 수밖에 없던 상태입니다. 3.0.0 부터 Linux 는 전역·개별 모두 그대로 적용됩니다.

**연동 시 반드시 확인 — 응답의 `partitions[].overwrite` 는 요청값의 반향이 아니라 실제로 적용된 값입니다.** Windows 대상에 `"allow"` 를 보내도 응답에는 **`"Not overwritten"`** 이 담깁니다.

```json
{
  "success": true,
  "data": {
    "notices": [
      "The overwrite option is Linux-only and was ignored for this Windows recovery job."
    ]
  }
}
```

`POST /recoveries` · `POST /recoveries/image` 양쪽 동일합니다. `JOB-ERROR-56` 자체는 남아 있습니다 — Linux 대상에 루트 파티션이 없어 매핑이 불가능한 경우에 쓰입니다.

**동작 변경 — 대상 서버가 사용 중일 때 (등록은 허용, 실행만 거부)**

같은 대상 서버 디스크에 복구가 둘 붙으면 나중 작업이 앞선 작업의 결과를 덮어씁니다. v2.0.2 까지는 이를 막는 검사가 없어 두 복구가 동시에 진행될 수 있었습니다. v3.0.0 은 이를 막되, **막는 지점을 등록이 아니라 실행에 둡니다** — 사전에 등록해 두고 나중에 시작하는 것은 정상적인 사용 방식이므로 등록은 언제나 허용합니다.

| 경로 | v2.0.2 | v3.0.0 |
|---|---|---|
| `POST /recoveries` · `POST /recoveries/image` (`autoStart` 없음) | 검사 없음 | 등록 성공 + `notices` 안내 |
| `POST /recoveries` · `POST /recoveries/image` (`autoStart: "use"`) | 검사 없음 — 대상이 사용 중이어도 즉시 실행 | **등록 성공.** 자동 시작만 생략 + `notices` 안내 |
| `PUT /recoveries/:identifier` (`status: "start"`) | 검사 없음 | **`JOB-ERROR-64` (409) 로 거부** |
| `PUT /recoveries/:identifier` (`status: "stop"`) | 검사 없음 | 제한 없음 |

**연동 시 반드시 확인 — 응답의 `common.autoStart` 는 요청값의 반향이 아니라 실제로 적용된 값입니다.** `autoStart: "use"` 로 등록해도 대상 서버가 사용 중이면 자동 시작이 생략되고, 응답에는 **`"not use"` 가 담깁니다.** 요청값과 응답값이 같다고 가정하고 화면을 그리면 "시작됨" 으로 잘못 표시됩니다. 등록 직후 상태는 **응답의 `common.autoStart` 값을 그대로** 쓰세요.

자동 시작이 생략된 이유는 `notices` 로 전달됩니다.

`autoStart: "use"` 로 등록했으나 대상 서버가 사용 중이었던 응답 (일부 발췌):

```json
{
  "success": true,
  "data": {
    "common": {
      "state": "success",
      "jobName": "nightly-recovery",
      "autoStart": "not use"
    },
    "notices": [
      "Recovery job 'daily-recovery' is currently in progress on target server 'target-server' — this job was registered but autoStart was skipped. Start it with a status update once the running job completes."
    ]
  }
}
```

`autoStart` 없이 등록한 경우에도 대상 서버가 사용 중이면 안내가 담깁니다 — `... — this job was registered but not started.`

자동 시작이 생략된 작업은 진행 중인 복구가 끝난 뒤 `PUT /recoveries/:identifier` 에 `status: "start"` 를 보내 실행하세요. 그때도 대상 서버가 여전히 사용 중이면 `JOB-ERROR-64` (409) 로 거부됩니다. 시작하려는 **그 작업 자신의 진행 이력은 차단 근거가 아니므로**, 같은 작업을 다시 시작하는 요청이 자기 자신 때문에 막히지는 않습니다.

진행 중 복구를 확인하는 조회 자체가 실패하면 등록도 실행도 막지 않습니다 — 확인이 되지 않는다는 이유로 정상 요청을 거부하지 않습니다.

|---|---|---|
| `data` | 전체 라이선스 **배열** (식별자 무시) | **단건 객체** |
| `message` | `License information list` | **`License information retrieved`** |
| 없는 식별자 | 200 + 전체 목록 | **404 `LICENSE-ERROR-01`** |

v2.0.2 까지는 이 경로가 `GET /licenses` 와 같은 응답을 냈고, 문서에도 "식별자는 서버에서 무시된다" 고 적혀 있었습니다. **응답에서 `data[0]` 을 꺼내 쓰거나, 없는 식별자에도 200 이 오는 것에 기대던 클라이언트는 수정이 필요합니다.**

`category` · `exp` · `created` 는 이 경로에서도 조회 조건으로 적용되며, 라이선스가 있어도 조건과 맞지 않으면 404 입니다. `center` 는 단건 조회에서 조회 범위를 좁히지 않습니다 — 보내도 오류가 되지 않고 무시됩니다.

**이름으로 조회할 때 정확일치입니다.** 종전에는 목록 검색용 부분일치를 그대로 썼기 때문에
`GET /licenses/abc` 가 `abc` 는 없고 `abcd` 만 있어도 **`abcd` 를 200 으로 반환**했습니다 —
지목하지 않은 리소스를 성공으로 돌려주던 셈입니다. **부분일치로 우연히 잡히던 요청은 이제 404** 입니다.
부분 검색이 필요하면 목록의 `name` 필터를 쓰세요 — 그쪽은 종전대로 부분일치입니다.

자세한 내용은 [GET /licenses/:identifier](/zdm/ko/api/3.0.0/docs/license/get) 참조.

**BREAKING — 단건 모니터링에서 `status` 조회 파라미터 제거**

작업 기준 모니터링 네 경로에서 `status` 를 받지 않습니다 — `GET /backups/monitoring/job/:identifier`,
`GET /replications/monitoring/job/:identifier` (v1 경로도 같은 스키마를 씁니다),
`GET /os-replications/monitoring/job/:identifier`.

| | v2.0.2 | v3.0.0 |
|---|---|---|
| `?status=` 전송 | 조회 조건으로 적용 | **400 `DTO-VALIDATION-03`** |
| 상태가 어긋날 때 | 404 (작업은 있는데 조건 불일치) | 해당 없음 |

경로 `identifier` 로 이미 작업 하나를 지목한 단건 조회입니다. 여기에 상태를 조건으로 더하면 어긋났을 때
404 가 되어 **"작업이 없다" 와 "있는데 상태가 다르다" 가 한 응답에 뭉개집니다.** 받는 쪽은 재시도할지
포기할지 판단할 수 없습니다. **상태는 응답의 `job.progressInfo.status`(backup) · `job.progress.status`
(replication · os-replication) 를 읽으면 됩니다.**

상태로 거르는 조회가 필요하면 컬렉션을 쓰십시오 — 서버 기준 모니터링(`GET /backups/monitoring/system/:identifier`)
과 목록 조회(`GET /replications?status=`) 의 `status` 는 배열을 거르는 필터로 그대로 있으며, 0 건이면
404 가 아니라 빈 결과입니다.

`?status=` 를 붙여 두던 클라이언트는 **파라미터를 빼야 합니다.** 조용히 무시되지 않고 400 으로 거절됩니다.

덧붙여 replication · os-replication 의 이 경로에서는 `scheduled` · `registered` 가 **원래부터 매칭되지
않았습니다** — 상태를 실행 중인 활성 작업에서 계산하므로 그 두 값이 나올 수 없어 언제나 404 였습니다.
파라미터가 사라지면서 이 함정도 없어집니다.

자세한 내용은 [백업 작업 기준 모니터링](/zdm/ko/api/3.0.0/docs/backup/monitoring-job) ·
[복제 작업 기준 모니터링](/zdm/ko/api/3.0.0/docs/replication/monitoring-job) ·
[OS 복제 작업 기준 모니터링](/zdm/ko/api/3.0.0/docs/os-replication/monitoring-job) 참조.

**BREAKING — 조회 파라미터 검증 강화**

조회(query) 파라미터는 **스키마에 선언된 이름만** 받습니다. 오타이거나 제거된 파라미터를 보내면
`DTO-VALIDATION-03` (400) 으로 거절되고, `details` 의 **key 가 문제 파라미터 이름**입니다.

v2.0.2 까지는 모르는 키가 조용히 버려져 **필터가 적용되지 않은 더 넓은 결과가 200 으로** 나갔습니다.
받는 쪽은 요청이 어긋난 사실조차 알 수 없었습니다.

```json
{
  "success": false,
  "error": {
    "code": "DTO-VALIDATION-03",
    "message": "Query parameter validation failed.",
    "details": {
      "sort": ["sort is not a supported parameter. Check for a typo or a parameter that has been removed."]
    }
  }
}
```

| | v2.0.2 | v3.0.0 |
|---|---|---|
| 선언되지 않은 query 파라미터 | 무시하고 200 (필터 누락) | **400 거부** |

같은 응답에 필수 누락과 모르는 키가 함께 있으면 각자 제 메시지를 유지합니다.

**동작 변경 — 조회 열거형 값의 대소문자**

조회·모니터링의 `status` / `mode` / `platform` / `repositoryType` / `serverType` 은 **대소문자를 구분하지 않습니다.**

응답에 실린 값(`"Processing"`)을 그대로 필터로 되돌려 보낼 수 있습니다. v2.0.2 까지는 요청 어휘가 소문자
(`processing`)여서 **API 가 만든 값을 API 가 400 으로 거절**했습니다.

**신규 — 저장소 스캔 커버리지 `scan`**

여러 저장소를 훑는 이미지 조회(`GET /backups/images`, `GET /backups/images/server/:server`)는
저장소 하나가 실패해도 나머지 결과를 200 으로 돌려줍니다. **그 사실이 응답의 `scan` 필드에 담깁니다.**

```json
"scan": {
  "total": 3, "succeeded": 2, "failed": 1,
  "failures": [{
    "centerName": "zdm-center-01",
    "repositoryId": 13,
    "code": "JOB-ERROR-68",
    "reason": "Backup image lookup timed out (...)",
    "retryable": true
  }]
}
```

**실패가 없어도 항상 포함됩니다** — `failed: 0` 이 곧 "목록이 완전하다" 는 신호입니다.
실패했을 때만 실으면 이 필드를 모르는 클라이언트가 부분 결과를 전체로 오인합니다.

`retryable` 은 다시 호출하면 풀릴 수 있는 실패인지를 나타냅니다(타임아웃·락 경합 `true`, 저장소 미존재 등 `false`).
부분 결과일 때는 `message` 도 `Backup images retrieved (2 of 3 repositories scanned)` 로 바뀝니다.

v2.0.2 까지는 실패한 저장소가 **서버 로그에만** 남아, 받는 쪽은 목록이 불완전하다는 사실조차 알 수 없었습니다.

**응답 값 변경**

- 작업 등록 직후 조회 시 `time.start` 가 `"-"` 로 표시됩니다 — 시작 시각은 데몬이 작업을 실제로 시작할 때 기록합니다.
- 라이선스 조회의 `dates.created` 가 실제 생성일을 반환합니다.
- **모니터링의 작업 상태가 작업 본체를 따릅니다.** 진행 정보 행(복구는 파티션마다 한 행)이 종료 단계에 들어가도, 작업 본체가 아직 진행 중이면 `Processing` 입니다 — v2.0.2 까지는 그 행만 보고 `Complete` 로 표시했습니다. 행의 종료는 **그 파티션의 복사**가 끝났다는 뜻이고 복구는 그 뒤에 재부팅 같은 후속 단계가 남습니다. 따라서 **`percent` 가 `"100%"` 인데 `status` 가 `Processing` 인 것은 모순이 아닙니다.** 완료 판정은 `status` 로만 하세요.
- **실패로 끝난 작업이 `Error` 로 표시됩니다.** 작업 본체가 실패로 종결됐는데도 진행 정보 행이 종료 단계면 `Complete` 로 나가던 것을 고쳤습니다.
