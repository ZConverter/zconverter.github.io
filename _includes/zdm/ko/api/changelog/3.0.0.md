**모든 엔드포인트의 응답 형식이 바뀝니다.** 응답을 파싱하는 모든 클라이언트는 수정이 필요합니다.

---

**BREAKING — `error` 가 문자열에서 객체로**

에러 응답의 `error` 필드가 문자열에서 `{ code, message, details? }` 객체로 바뀝니다.

- **이전**: `"error": "Specified partition does not exist on the server."`
- **이후**: `"error": { "code": "JOB-ERROR-13", "message": "Specified partition does not exist on the server." }`

`error.code` 는 안정 식별자입니다. **클라이언트는 메시지 문자열이 아니라 이 값으로 분기하세요** — 메시지 문구는 예고 없이 바뀝니다. 전체 목록은 [에러 코드](/zdm/ko/api/3.0.0/docs/error-codes) 참조.

기존 최상위 `detail.validationErrors` 는 **`error.details` 로 흡수**됩니다. 검증 실패일 때만 응답 모양이 달라지던 변형이 사라지고 모든 에러가 한 형태가 됩니다.

```json
{
  "success": false,
  "traceId": "a1b2c3d4e5f60718293a4b5c6d7e8f90",
  "error": {
    "code": "DTO-VALIDATION-01",
    "message": "Request body validation failed.",
    "details": { "center": ["center is required"] }
  },
  "timestamp": "2026-08-28T10:30:00.000+09:00"
}
```

---

**BREAKING — `requestID` 가 `traceId` 로**

응답 본문의 `requestID` 키 이름이 `traceId` 로 바뀝니다. **성공 응답에도 적용됩니다.**

값은 그대로이며, 응답 헤더 `X-Trace-Id` · 서버 로그의 `traceId` 와 **완전히 같은 값**입니다. 장애 문의 시 이 값을 전달하면 서버 로그를 바로 찾을 수 있습니다.

---

**BREAKING — `timestamp` 가 ISO 8601 로**

- **이전**: `"2026-08-28 10:30:00"` (타임존·밀리초 없음)
- **이후**: `"2026-08-28T10:30:00.123+09:00"`

기존 형식은 타임존이 없어 클라이언트가 시각을 확정할 수 없었습니다. **성공 응답에도 적용됩니다.**

---

**신규 — `POST /recoveries/image` (Image Recovery)**

source 서버 없이 backup image 파일명만으로 복구를 등록합니다. source 서버가 ZDM 에서 삭제된 뒤에도 이미지가 저장소에 남아 있으면 복구할 수 있습니다.

각 이미지의 원본 파티션과 소속 백업 작업은 저장소의 이미지 정보에서 자동으로 읽습니다. 자세한 내용은 [POST /recoveries/image](/zdm/ko/api/3.0.0/docs/recovery/image-regist) 참조.

---

**동작 변경 — 복구 파티션 매핑 규칙**

**하나의 대상 파티션은 같은 원본 파티션의 이미지를 최대 1장만 받습니다.** 위반 시 `JOB-ERROR-55` (400) 로 거부됩니다.

같은 파티션을 서로 다른 시점에 백업한 이미지 두 장을 한 파티션에 함께 복구하면, 나중에 복구된 이미지가 앞선 것을 덮어써 결과가 결정되지 않습니다. 이전에는 이 요청이 통과해 복구 결과를 예측할 수 없었습니다.

| 배치 | v2.0.2 | v3.0.0 |
|---|---|---|
| 한 대상 파티션에 같은 원본의 이미지 2장 | 통과 (결과 비결정적) | **400 거부** |
| 같은 원본의 이미지를 서로 다른 대상 파티션에 1장씩 | 거부 | **허용** |
| 원본이 다른 이미지를 한 대상 파티션에 | 허용 | 허용 |

함께 **하나의 원본 파티션을 여러 대상 파티션으로 보내는 매핑(1:N)이 허용**됩니다. 이전에는 원본 파티션이 두 번 등장하면 거부됐습니다.

---

**동작 변경 — 복구 등록의 저장소 해석 실패**

`jobList[].repository.id` 가 center 에 존재하지 않으면 `ZDM-REPOSITORY-ERROR-01` (404) 로 원인을 밝혀 실패합니다. 응답 메시지에 **사용 가능한 저장소 ID 목록**이 함께 담깁니다. 이전에는 내부 오류로 뭉개져 원인을 알 수 없었습니다.

---

**동작 변경 — 복구 등록의 전량 skip 응답**

backup 작업·이미지가 없어 모든 파티션이 제외되면 `JOB-ERROR-14` (400) 를 반환하며, **각 파티션이 왜 제외됐는지가 메시지에 함께 담깁니다.** 이전에는 `JOB-ERROR-01` (404) 한 줄이라 원인을 알 수 없었습니다.

---

**신규 문서 — 에러 코드 총람**

API 가 반환하는 에러 코드 전체 목록을 [에러 코드](/zdm/ko/api/3.0.0/docs/error-codes) 페이지에 정리했습니다. 코드 대역·HTTP 상태·설명을 도메인별로 확인할 수 있습니다.

---

**응답 값 변경**

- 작업 등록 직후 조회 시 `time.start` 가 `"-"` 로 표시됩니다 — 시작 시각은 데몬이 작업을 실제로 시작할 때 기록합니다.
- 라이선스 조회의 `dates.created` 가 실제 생성일을 반환합니다.
